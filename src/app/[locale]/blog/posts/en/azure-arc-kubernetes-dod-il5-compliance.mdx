## Azure Arc-Enabled Kubernetes for DoD IL5 Compliance: A Senior Engineer's Playbook

If you're operating Kubernetes workloads in a DoD environment and you haven't fully evaluated Azure Arc as your compliance enforcement layer, you're leaving a significant capability gap open. I've spent considerable time architecting IL4 and IL5 environments across Azure Government and GCC High tenants, and Azure Arc-enabled Kubernetes has become one of the most powerful tools in my compliance automation arsenal. This post walks you through the full implementation — from onboarding to GitOps-driven policy enforcement — with a specific focus on what the DoD IL5 provisional authorization actually requires.

---

## What Azure Arc-Enabled Kubernetes Is and Why It Matters for IL5

Azure Arc-enabled Kubernetes extends Azure's control plane to any Kubernetes cluster — whether it's running on-premises, in Azure Government, or in a hybrid edge environment. From a compliance posture standpoint, this matters enormously because DoD IL5 workloads must meet NIST SP 800-53 Revision 5 High baseline controls, and Azure Arc gives you the centralized enforcement mechanism to address those controls consistently across heterogeneous infrastructure.

The DoD IL5 designation covers Controlled Unclassified Information (CUI) at higher sensitivity levels and some National Security Systems data. The key differentiator from IL4 is the expanded security control requirements — particularly around access control (AC), audit and accountability (AU), system and communications protection (SC), and configuration management (CM). Azure Arc addresses all four families directly through:

- **Azure Policy for Kubernetes (Gatekeeper OPA)** — enforces CM and AC controls at admission time
- **Microsoft Defender for Containers** — covers SI (System and Information Integrity) controls
- **GitOps with Flux v2** — enforces CM-2, CM-3, and CM-6 baseline configuration controls
- **Azure Monitor and Log Analytics in Government regions** — satisfies AU-2, AU-3, AU-9, and AU-12

The DoD Cloud Computing Security Requirements Guide (CC SRG) and the accompanying DISA STIG for Kubernetes v1R6 are your reference documents here. Azure Arc's integration with Azure Policy maps directly to those STIGs.

## Step-by-Step: Onboarding Your Kubernetes Cluster to Azure Arc

### Step 1: Create the Resource Group and Arc-Connected Cluster

For IL5 environments, I strongly recommend placing your Arc resources in a dedicated resource group with a defined resource lock and Azure Policy scope assignment from day one.

### Step 2: Deploy GitOps Configuration with Flux v2

CM-2 (Baseline Configuration) and CM-6 (Configuration Settings) under NIST 800-53 require that all configuration changes are controlled, audited, and traceable. Flux v2 through Azure Arc's `k8s-configuration` extension is how I enforce this. Your Git repository becomes the authoritative source of truth, and any drift from that state is automatically remediated.

```bash
# Enable the GitOps extension on the connected cluster
az k8s-configuration flux create \
  --name "il5-baseline-config" \
  --cluster-name $CLUSTER_NAME \
  --resource-group $RG \
  --cluster-type connectedClusters \
  --url https://github.com/your-agency/k8s-il5-manifests \
  --branch main \
  --namespace flux-system \
  --scope cluster \
  --kustomization name=baseline path=./clusters/il5-prod prune=true sync_interval=5m
```

Critically, your Git repository **must** be private and authenticated via SSH key or PAT stored in Azure Key Vault (Government endpoint). Do not use public repositories for IL5 manifests.

## Deploying IL5 Hardened Namespace Configuration via Bicep

Infrastructure-as-code is mandatory for IL5 environments — manual configuration does not satisfy CM-3 (Configuration Change Control). Here's a Bicep module I use to deploy a hardened namespace with resource quotas and network policy annotations:

```bicep
// modules/il5-namespace.bicep
param clusterName string
param namespaceName string
param resourceGroupName string

resource arcCluster 'Microsoft.Kubernetes/connectedClusters@2021-10-01' existing = {
  name: clusterName
  scope: resourceGroup(resourceGroupName)
}

resource namespaceConfig 'Microsoft.KubernetesConfiguration/extensions@2022-11-01' = {
  name: 'il5-namespace-baseline'
  scope: arcCluster
  properties: {
    extensionType: 'microsoft.flux'
    autoUpgradeMinorVersion: true
    configurationSettings: {
      'multiTenancy.enforce': 'true'
      'helm.enabled': 'false'
    }
    configurationProtectedSettings: {}
    releaseTrain: 'Stable'
    scope: {
      cluster: {
        releaseNamespace: 'flux-system'
      }
    }
  }
}
```

## KQL Queries for Compliance Monitoring and AU Control Evidence

Audit and Accountability (AU) controls require that you can produce evidence of logging, log protection, and anomaly detection. These KQL queries against your Log Analytics workspace in Azure Government give you that evidence.

<CodeBlock
  className="custom-code-block"
  liveEditor
  codeInstances={[
    {
      code: `// AU-2: Detect privileged container creation attempts on Arc-managed clusters
// Run in Log Analytics workspace connected to your Arc cluster
AzureDiagnostics
| where ResourceType == "CONNECTEDCLUSTERS"
| where Category == "kube-audit"
| where log_s contains "privileged"
| extend parsed = parse_json(log_s)
| where parsed.verb == "create"
| project
    TimeGenerated,
    ClusterName = Resource,
    RequestUser = parsed.user.username,
    Namespace = parsed.objectRef.namespace,
    Resource = parsed.objectRef.resource,
    ResponseCode = parsed.responseStatus.code
| where ResponseCode != 403  // Flag any that weren't denied
| order by TimeGenerated desc

// AU-12: Verify Arc agent heartbeat continuity (detect gaps > 10 minutes)
ArcK8sAudit
| where TimeGenerated > ago(24h)
| summarize LastSeen = max(TimeGenerated) by ClusterName = _ResourceId
| extend MinutesSinceLastSeen = datetime_diff('minute', now(), LastSeen)
| where MinutesSinceLastSeen > 10
| project ClusterName, LastSeen, MinutesSinceLastSeen
| order by MinutesSinceLastSeen desc

// CM-7: Identify non-compliant resources against assigned IL5 policy
PolicyInsights
| where TimeGenerated > ago(7d)
| where PolicyAssignmentName contains "il5"
| where ComplianceState == "NonCompliant"
| summarize NonCompliantCount = count() by
    PolicyDefinitionName,
    ResourceType,
    ResourceGroup
| order by NonCompliantCount desc`,

## Common Pitfalls and How to Avoid Them

**1. Using commercial endpoints in government tenants.** Always verify `az cloud show` returns `AzureUSGovernment`. Arc agents will silently fail health checks if they attempt to reach `management.azure.com` instead of `management.usgovcloudapi.net`.

**2. Not scoping Flux to a private, authenticated repo.** IL5 prohibits the use of unauthenticated public endpoints for configuration delivery. Store your SSH deploy key as a Key Vault secret and reference it in your Flux `GitRepository` object.

**3. Deploying Arc agents without proxy configuration in air-gapped environments.** If your IL5 cluster sits behind an HTTP proxy or in a network segment without direct internet, configure the `--proxy-https` and `--proxy-http` flags during `az connectedk8s connect`. Forgetting this causes the `azure-arc-agent` pod to crashloop indefinitely.

**4. Assigning policy in report-only mode and calling it compliance.** `--enforcement-mode DoNotEnforce` is useful for initial assessment, but IL5 requires actual enforcement. Flip to `Default` enforcement mode before any ATO evidence package submission.

**5. Overlooking DISA Kubernetes STIG controls not covered by the NIST initiative.** The built-in NIST 800-53 Rev 5 initiative is a good baseline but doesn't cover every STIG check. Write custom Azure Policy definitions for things like `V-242386` (audit log rotation) and `V-242415` (no anonymous API server access).
