## AKS Hardening with CIS Benchmark and Azure Policy: A FedRAMP-Ready Implementation Guide

If you're running containerized workloads in a DoD or federal civilian environment, AKS hardening isn't optional — it's a compliance mandate. I've spent considerable time implementing CIS Kubernetes Benchmark controls across Azure Government (GCC High) and DoD IL4/IL5 environments, and the gap between "deployed AKS" and "audit-ready AKS" is substantial. This post walks you through exactly how I close that gap using Azure Policy, the CIS AKS Benchmark, and a fully automated DevSecOps pipeline.

---

## Why CIS Benchmark + Azure Policy Matters for GovCloud and FedRAMP

The **CIS Azure Kubernetes Service Benchmark** (currently v1.5.0) provides prescriptive hardening guidance mapped directly to Kubernetes control plane and data plane configurations. For FedRAMP Moderate/High and DoD IL4/IL5 authorizations, your AKS clusters must demonstrate compliance with a subset of **NIST SP 800-53 Rev 5** controls — particularly:

- **SI-3 / SI-7** — Malicious code protection and software integrity
- **AC-3 / AC-6** — Access enforcement and least privilege (RBAC, Pod Security)
- **CM-6 / CM-7** — Configuration settings and least functionality
- **AU-2 / AU-12** — Audit events and audit record generation
- **SC-7 / SC-28** — Boundary protection and data at rest encryption

Azure Policy's **built-in initiative `[Preview]: [AKS] CIS Kubernetes Benchmark`** and the **Azure Security Benchmark for Kubernetes** give you the enforcement layer. But raw initiative assignment alone won't get you there. You need node pool hardening, admission controllers, network policies, and continuous compliance telemetry — all wired into your pipeline.

## Step 2: Deploy a Hardened AKS Cluster with Bicep

Don't try to harden a running production cluster ad hoc. Build hardening into your IaC from day one. Here's the Bicep configuration I use for FedRAMP-aligned AKS deployments in Azure Government:

  name: clusterName

## Step 4: Enforce Namespace-Level Pod Security Admission

Post-PSP deprecation (Kubernetes 1.25+), Pod Security Admission (PSA) is your built-in enforcement layer. Label your namespaces correctly — this is a CIS 5.2.x requirement and maps directly to **NIST AC-6 (Least Privilege)**:

```bash
# Apply restricted policy to all application namespaces
kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.29 \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted

# Baseline for monitoring/logging namespaces
kubectl label namespace monitoring \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

Pair this with a Network Policy that defaults-deny all ingress/egress at the namespace level, then allowlist only required paths — satisfying **NIST SC-7 (Boundary Protection)**.

## Step 5: Continuous Compliance Monitoring with KQL

Policy assignments give you compliance state, but you need operational visibility. I use this KQL query in Log Analytics / Azure Monitor Workbooks to surface non-compliant AKS resources continuously:

```kql
// KQL: AKS CIS Compliance — Non-compliant resources with control mapping
PolicyResources
| where type == "microsoft.policyinsights/policystates"
| where properties.complianceState == "NonCompliant"
| where properties.resourceType contains "containerService"
| extend
    PolicyName = tostring(properties.policyDefinitionName),
    PolicyEffect = tostring(properties.policyDefinitionAction),
    ResourceName = tostring(properties.resourceDetails.resourceId),
    EvaluationTime = todatetime(properties.timestamp),
    InitiativeName = tostring(properties.policySetDefinitionName)
| where InitiativeName contains "CIS" or InitiativeName contains "FedRAMP"
| summarize
    FailureCount = count(),
    AffectedResources = make_set(ResourceName),
    LastEvaluated = max(EvaluationTime)
    by PolicyName, PolicyEffect, InitiativeName
| order by FailureCount desc
| project
    InitiativeName,
    PolicyName,
    PolicyEffect,
    FailureCount,
    AffectedResources,
    LastEvaluated
```

Export this to a Power BI dashboard or wire it into your SIEM (Microsoft Sentinel) for continuous ATO monitoring. This directly supports **NIST CA-7 (Continuous Monitoring)** and closes the evidence loop for your SSP.

## Common Pitfalls and How I Avoid Them

**1. Assigning Deny-mode policies without exclusion lists**
Blanket `Deny` enforcement on kube-system and azure-specific namespaces will break cluster operations immediately. Always seed your `excludedNamespaces` parameter with `["kube-system", "gatekeeper-system", "azure-arc", "azure-extensions-usage-system"]` before going to `Deny` mode.

**2. Ignoring the azurePolicy add-on prerequisite**
Azure Policy for Kubernetes runs as an in-cluster Gatekeeper admission controller. If the add-on isn't enabled, your policy assignments show as compliant vacuously. I've seen audit findings fail because teams thought portal-level policy was enforcing — it wasn't.

**3. Conflating Azure RBAC with Kubernetes RBAC**
`enableAzureRBAC: true` routes kubectl authorization through Azure AD, but you still need K8s ClusterRoleBindings for service accounts and workload identity. These are separate planes. Confusion here creates both security gaps and access outages.
