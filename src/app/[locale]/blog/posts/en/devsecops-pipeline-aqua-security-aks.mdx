## DevSecOps Pipeline with Aqua Security on AKS: A FedRAMP-Ready Implementation Guide

If you're operating Kubernetes workloads in a DoD or federal civilian environment, you already know that container security isn't optional — it's a compliance requirement baked into FedRAMP High, DoD IL4/IL5, and every NIST 800-53 Rev 5 control family that touches SI, CM, and AU. What I see too often in federal engagements is teams bolting security onto the tail end of a pipeline as an afterthought. That doesn't fly in a GovCloud environment where an ATO is on the line.

In this post, I'm walking you through a production-grade DevSecOps pipeline that integrates Aqua Security with Azure Kubernetes Service (AKS) inside Azure Government (GCC High). This covers image scanning, runtime enforcement, policy-as-code gates, and audit trail generation — all mapped to real NIST controls. Let's get into it.

---

## Why Aqua Security + AKS for FedRAMP Environments

Aqua Security is one of the few container security platforms that has FedRAMP authorization precedent and deep integration with both Azure Defender for Containers and Azure Policy. On AKS, it operates as a DaemonSet-deployed enforcer with a centralized SaaS or self-hosted console, giving you:

- **Image assurance policies** — block non-compliant images from running
- **Runtime protection** — behavioral drift detection and process whitelisting
- **CSPM posture scoring** — continuous misconfiguration detection across your cluster
- **eBPF-based enforcement** — low-overhead kernel-level activity monitoring
- **Audit trail export** — structured event logs consumable by Azure Monitor and Microsoft Sentinel

For GovCloud, the critical requirement is that Aqua's data plane (the enforcer) runs inside your AKS cluster within your Azure Government subscription boundary. The control plane can be Aqua's SaaS offering (confirm their FedRAMP boundary with their CSP documentation) or self-hosted on AKS itself. For IL5 workloads, I always recommend self-hosted to keep data sovereignty clean.

**NIST 800-53 Rev 5 Controls Addressed:**

| Control | Description |
|---|---|
| SI-3 | Malicious Code Protection |
| SI-7 | Software, Firmware, and Information Integrity |
| CM-7 | Least Functionality |
| CM-11 | User-Installed Software |
| AU-2, AU-12 | Audit Events / Audit Record Generation |
| RA-5 | Vulnerability Scanning |
| SA-11 | Developer Testing and Evaluation |
| CA-7 | Continuous Monitoring |

## Architecture Overview

The pipeline I'm describing follows this flow:

```
Developer Push → GitHub Actions / Azure DevOps → Aqua Image Scan (CI Gate) →
Azure Container Registry (ACR) → Aqua Registry Scan → AKS Admission Controller
(Aqua Enforcer) → Runtime Policy Enforcement → Logs → Azure Monitor / Sentinel
```

Everything runs inside Azure Government with private endpoints. No public egress for image pulls or scan results.

Aqua's enforcer is deployed as a privileged DaemonSet. In FedRAMP environments, you need to explicitly document this privileged container exemption in your SSP. The enforcer requires host-level access to mount namespaces for eBPF enforcement.

  pod-security.kubernetes.io/warn=restricted

# Create Aqua registry secret (pull from Aqua's private registry)

## Step 3: CI Pipeline Gate — Image Scanning in Azure DevOps

This is the shift-left piece. Every image built in your pipeline must pass Aqua's image assurance scan before it gets pushed to ACR. A failed scan breaks the build — not just generates a warning.

<CodeBlock className="custom-code-block" liveEditor codeInstances={[{ code: `# azure-pipelines.yml — DevSecOps pipeline with Aqua scan gate

trigger:
  branches:
    include:
      - main
      - release/*

variables:
  acrName: acrfedrampgov
  imageName: myapp
  imageTag: $(Build.BuildId)
  aquaScannerImage: registry.aquasec.com/scanner:2022.4

stages:
  - stage: Build
    displayName: Build and Scan
    jobs:
      - job: BuildImage
        pool:
          name: AzureGovSelfHosted
        steps:
          - task: Docker@2
            displayName: Build Docker Image
            inputs:
              command: build
              repository: $(acrName).azurecr.us/$(imageName)
              tags: $(imageTag)
              Dockerfile: Dockerfile

          - script: |
              docker run --rm \
                -v /var/run/docker.sock:/var/run/docker.sock \
                -e AQUA_TOKEN=$(AQUA_TOKEN) \
                -e AQUA_HOST=$(AQUA_HOST) \
                $(aquaScannerImage) \
                scan \
                --host $(AQUA_HOST) \
                --token $(AQUA_TOKEN) \
                --image $(acrName).azurecr.us/$(imageName):$(imageTag) \
                --register \
                --registry "Azure-Gov-ACR" \
                --policies "fedramp-high-policy" \
                --htmlfile $(Build.ArtifactStagingDirectory)/aqua-scan-report.html \
                --jsonfile $(Build.ArtifactStagingDirectory)/aqua-scan-results.json
            displayName: Aqua Image Scan Gate
            env:
              AQUA_TOKEN: $(AQUA_TOKEN)
              AQUA_HOST: $(AQUA_HOST)

          - task: PublishBuildArtifacts@1
            displayName: Publish Scan Report
            inputs:
              pathToPublish: $(Build.ArtifactStagingDirectory)
              artifactName: SecurityReports
            condition: always()

          - task: Docker@2
            displayName: Push to ACR (only if scan passed)
            inputs:
              command: push
              repository: $(acrName).azurecr.us/$(imageName)
              tags: $(imageTag)
            condition: succeeded()`, label: "Azure DevOps Pipeline with Aqua Gate", language: "yaml" }]} copyButton />

The `--policies "fedramp-high-policy"` flag references a named policy in your Aqua console that I configure to block on:
- Any CRITICAL CVE with a fix available
- HIGH CVEs with CVSS ≥ 8.0 and a fix available
- Images running as root (UID 0)
- Images with embedded secrets detected by Aqua's secret scanner
- Images not built from an approved base image list

This gives you a documented, auditable gate that maps directly to RA-5 (Vulnerability Scanning) and SA-11 (Developer Security Testing).

## Step 4: Admission Control — Preventing Non-Compliant Deployments

Even with CI scanning, you need a runtime gate at the Kubernetes API level. Aqua's enforcer acts as a Kubernetes admission webhook. Here's how to validate it's working and write a KQL query to monitor denials in your Log Analytics workspace:

<CodeBlock className="custom-code-block" liveEditor codeInstances={[{ code: `# Verify Aqua admission webhook registration
kubectl get mutatingwebhookconfigurations | grep aqua
kubectl get validatingwebhookconfigurations | grep aqua

# Check enforcer audit events flowing to stdout
kubectl logs -n aqua -l app=aqua-enforcer --tail=100 | grep -E "BLOCK|ALLOW|AUDIT"

# KQL Query — Aqua Enforcement Events in Log Analytics
# Run this in your Azure Government Log Analytics workspace

ContainerLog
| where LogEntry contains "aqua"
| where LogEntry contains "block" or LogEntry contains "enforce"
| extend ParsedLog = parse_json(LogEntry)
| project 
    TimeGenerated,
    ClusterName = tostring(ParsedLog.cluster),
    Namespace = tostring(ParsedLog.namespace),
    PodName = tostring(ParsedLog.pod_name),
    ImageName = tostring(ParsedLog.image),
    Action = tostring(ParsedLog.action),
    PolicyName = tostring(ParsedLog.policy),
    Reason = tostring(ParsedLog.reason),
    UserIdentity = tostring(ParsedLog.user)
| where Action == "block"
| order by TimeGenerated desc
| summarize BlockCount=count() by ImageName, PolicyName, Reason, bin(TimeGenerated, 1h)`, label: "Admission Webhook Validation and KQL Monitoring", language: "bash" }]} copyButton />

This KQL query feeds a Microsoft Sentinel workbook I build for every FedRAMP engagement. It gives your ISSO a real-time dashboard of blocked deployments, which directly satisfies the CA-7 (Continuous Monitoring) requirement and provides the evidence artifacts needed during your 3PAO assessment.
